### Setup — Start LocalStack and create the log destination

LocalStack was started with its CloudWatch service port (`4566`) and service-port range exposed. The endpoint variable was then set so AWS CLI log commands were sent to LocalStack. A CloudWatch log group (`/ccse/app`) and an `auth` log stream were created.


### Task 2 — Centralise logs in CloudWatch

Each line in `auth.log` was read and submitted to the `/ccse/app` log group and `auth` stream. The timestamp variable was increased for each event, then `get-log-events` was used to confirm ingestion.

```bash
TS=$(date +%s000)
while IFS= read -r line; do
  aws $EP logs put-log-events --log-group-name /ccse/app --log-stream-name auth \
    --log-events timestamp=$TS,message="$line" >/dev/null
  TS=$((TS+1000))
done < auth.log

aws $EP logs get-log-events --log-group-name /ccse/app --log-stream-name auth \
  --query 'events[].message' --output text
```

- `put-log-events` sends each application log record to the central log service.
- `get-log-events` retrieves the stored messages, confirming that centralisation succeeded.

### Task 3 — Query security-relevant activity

The failed-login records were filtered and grouped by source IP address.

```bash

```

- `grep LOGIN_FAIL` selects failed authentication events.
- `awk` extracts the user and source-IP fields.
- `sort | uniq -c` groups identical results and counts them.

The result showed **four failed attempts** associated with `ip=203.0.113.9`, identifying a source that required investigation.

### Task 4 — Create tamper-proof, hash-chained logs

A hash chain was generated by hashing every log record together with the previous record's hash. A modified copy of the log was then made by changing the export size from `500MB` to `5MB`.

```bash
PREV=0
while IFS= read -r line; do
  H=$(printf '%s%s' "$PREV" "$line" | sha256sum | cut -d' ' -f1)
  printf '%s | %s\n' "$line" "$H"
  PREV=$H
done < auth.log > auth.chain

sed 's/500MB/5MB/' auth.log > auth.tampered
paste -d'|' <(cut -d'|' -f1 auth.chain) <(cut -d'|' -f2 auth.chain) >/dev/null
```

- The loop builds `auth.chain`, where each SHA-256 hash depends on the current event and the prior hash.
- `sed` creates a deliberately altered log for integrity testing.
- `paste` and `cut` align original chained fields for validation; a full verifier would recompute each hash and report the first mismatch.

Because later hashes depend on earlier values, modifying an event invalidates its own hash and every subsequent link unless the attacker can recompute and replace the protected chain.

### Task 5 — Detect an incident through correlation

Events for the suspicious IP address were counted across three types: failures, successful logins, and exports. The counts were evaluated together against a detection rule.

```bash
IP=203.0.113.9
FAILS=$(grep -c "LOGIN_FAIL.*$IP" auth.log)
SUCCESS=$(grep -c "LOGIN_OK.*$IP" auth.log)
EXPORT=$(grep -c "EXPORT_DATA.*$IP" auth.log)
echo "IP=$IP fails=$FAILS success=$SUCCESS export=$EXPORT"

if [ "$FAILS" -ge 3 ] && [ "$SUCCESS" -ge 1 ] && [ "$EXPORT" -ge 1 ]; then
  echo "ALERT: probable brute force -> compromise -> data exfiltration"
fi
```

- The three `grep -c` commands count relevant event types for one IP.
- The `if` statement correlates the counts and raises an alert only when the multi-stage pattern is present.

The rule returned: `IP=203.0.113.9 fails=4 success=1 export=1` and raised an alert for probable brute force, compromise, and data exfiltration.

![Evidence — Correlation rule and incident alert](<evidence/Task5-Detect the Incident(Correlation).png>)

### Task 6 — Incident response and evidence preservation

The suspicious source IP was blocked using an iptables rule. The original log was then copied into an evidence file and its SHA-256 checksum was created to support integrity verification.

```bash
docker run --rm --cap-add=NET_ADMIN alpine sh -c 'apk add -q iptables; iptables -A INPUT -s 203.0.113.9 -j DROP; iptables -L INPUT -n | tail -2'

cp auth.log evidence_$(date +%Y%m%d).log
sha256sum evidence_*.log > evidence.sha256
cat evidence.sha256
```

- The Docker command runs a temporary privileged network-administration container, adds a `DROP` rule for `203.0.113.9`, and displays the rule as confirmation.
- `cp` preserves a dated evidence copy of the log.
- `sha256sum` creates a checksum manifest; later recalculation can prove whether the preserved evidence changed.

## 5. Short-Answer Questions

**Q1. What is the difference between a log and an event? Give an example of each from this lab.**  
An event is a single occurrence, such as `LOGIN_FAIL` by `admin` from `203.0.113.9`. A log is the recorded entry or collection of records that documents events, such as `auth.log`.

**Q2. Why must audit logs be tamper-proof, and how does a hash chain achieve this?**  
They must be trustworthy for investigations and compliance. Each hash-chain value includes the previous hash, so changing one record breaks that record's hash and the following links.

**Q3. How did correlation detect an incident that no single log line revealed?**  
It combined four failures, one later successful login, and one export from the same IP. Together, these showed a likely brute-force attack, compromise, and exfiltration sequence.

**Q4. List the incident-response steps you performed and the goal of each.**  
Detection identified the suspicious pattern; containment blocked `203.0.113.9`; preservation copied the log; and hashing created an integrity check for the evidence.

**Q5. How do the same logs serve both security monitoring and compliance evidence (Weeks 6, 11)?**  
Monitoring uses the logs to detect and investigate threats in near real time. Compliance uses the same timestamped, centralised, integrity-protected records to demonstrate auditability and control operation.

## 6. Conclusion

The lab demonstrated an end-to-end monitoring workflow: collect application events, centralise them, query suspicious activity, protect their integrity, correlate them into an actionable alert, contain the suspected attacker, and preserve verifiable evidence.
